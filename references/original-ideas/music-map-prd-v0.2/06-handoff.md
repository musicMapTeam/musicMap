# 开发交接说明

## 1. 怎么使用这套交付

先读 PRD 的第 3—6 节，体验一次漫游和一次挑战，再对照原型说明与验收用例。原型用于讲清行为和视觉方向；正式实现可选搭子熟悉的技术，不要求照搬原型内部组织方式。

业务规则优先级：用户已确认需求 → PRD → 原型说明 / 流程图 → 原型演示代码。出现冲突时记录具体差异，不能默认把代码里的限制改成新需求。

## 2. 建议拆分的实现任务

| 顺序 | 工作项 | 交付结果 | 主责 |
|---|---|---|---|
| 1 | 数据与音频最小验证 | 一组可追溯真实关系、代表作与手机可播片段，说明缺失项 | 开发，产品抽查 |
| 2 | 状态和路由 | 独立漫游 / 挑战会话、当前路径、历史事件、保存恢复 | 开发 |
| 3 | 图谱漫游 | 搜索、旋转、切中心、查看依据、模式切换、返回 | 开发 |
| 4 | 真实试听与清单 | 单曲播放、留下 / 移除、结束回顾、本地历史 | 开发，产品验收 |
| 5 | 合作挑战 | 可达性、计步、回退、结果、与漫游衔接 | 开发 |
| 6 | 真实手机与异常 | 音频、手势、长内容、资源失败、保存失败 | 双方 |
| 7 | 公开部署与参赛材料 | 可访问链接、介绍、视频、封面、完整提交 | 开发部署；产品组织材料 |

各项可按搭子实际开发能力安排，但优先验证真实数据与试听；不要等视觉全部实现才发现资源不支持核心体验。风格模式能否进入正式首版由数据验证结果决定，调整范围时明确同步产品。

## 3. 状态约定

| 状态 / 数据 | 用途 | 关键约束 |
|---|---|---|
| activeSessionId | 当前操作会话 | 打开历史回顾不自动覆盖另一个活跃会话 |
| session.type | roam / challenge | 分开存储路线与歌曲 |
| session.status | active / ended / complete | 漫游结束可再继续；挑战到终点才 complete |
| path | 当前有效路径，起点起始 | 回退弹出一段；重置只保留起点 |
| events | 漫游完整操作事件 | 保留移动与导航事件，生成分支回顾 |
| savedTracks | 用户主动留下的曲目 | 按稳定录音 ID / 版本去重；与浏览、试听分离 |
| mode / view | 当前关系模式与视角 | 每个路径节点保留返回时需要的视图状态 |
| graphVersion | 本局数据版本 | 挑战固定；历史关系作品需保存快照 |
| returnRoamId | 进入挑战前的漫游 | 返回时优先恢复；不存在则新建漫游 |

挑战步数始终由 `path.length - 1` 推导，不用一个可独立漂移的计数器。完成结果显示有效路径，歌曲只是边上的依据，不额外计步。任何路径移动必须来自本局合法邻接关系。

保存当前路径和完整事件是两种不同目的：前者支持导航，后者解释探索过程。刷新后恢复视图与歌曲，但不自动恢复播放。

## 4. 数据接入与降级

- 数据到界面之间做一层转换，统一艺人、录音、关系、素材 ID；避免页面直接依赖某个下载文件的临时字段。
- 正式合作挑战只使用核验通过的合作关系；图中端点和作品必须存在。
- 保留来源和角色，不把生成模型的自由描述作为事实证据。首版无需自训练推荐模型或付费服务。
- 缺头像显示首字；缺某首试听显示不可用；全部核心试听不可用时应回到资源与范围评审，不能用模拟状态冒充正式完成。
- 历史存关系、作品的当时快照；数据更新不会悄悄改变用户已经走过的路。若旧版本不可恢复，允许看旧记录并明确提示另开新局。
- 本地存储读写应捕获异常；删除一条记录不清空全部会话。原型同地址内可持久化，正式版需在最终域名重新验收。

## 5. 上传与部署

建议将本交付包放入仓库的 `product/` 目录，README 增加入口。文件全部使用相对链接，保持目录结构即可。上传前先查看仓库自身的协作说明；本交付不要求覆盖现有开发代码。

原型是静态文件，可由团队选用的静态托管方式提供 HTTPS 访问。若项目已有部署机制，优先遵循项目现状；本文不假定 GitHub Pages 已开启或团队已具备某服务权限。

部署完成后检查：打开的是运行中的网页，不是 GitHub 源代码页；JS/CSS 的相对路径正确；手机从链接直接进入；刷新能加载；模拟原型与正式作品说明明确区分。正式参赛 Demo 需要真实数据与音频验收，原型链接不能被描述为真实音乐服务已经完成。

## 6. 分工与时间

产品已得到：PRD、流程图、交互原型、数据需求、验收用例、参赛文案与讲解脚本。产品后续重点是审阅体验、核对内容、组织试用与最终材料，不需要先学会写代码。

开发后续重点是资源验证、真实数据和音频接入、正式代码、手机性能与部署。团队成员个人信息、账号权限、最终素材来源和实际开发进度不能由本套文件替代确认。

内部建议 10 月 8 日形成稳定版本和材料，10 月 9 日检查上传并确认提交成功。个人发现卡片等增强项排在必需功能与材料之后。
